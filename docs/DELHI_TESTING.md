# Delhi automated gameplay testing (Phase T1: the test adapter)

Plan and reasons: `docs/DELHI_QA_T0.md`. Code: `src/debug/delhi_test_adapter.js` (development only; **nothing in the game imports it**, so a normal or bundled build never contains it, and no shared file such as `src/main.js` was changed).

## Use
1. Serve the project unbundled: `python3 tools/serve.py 8791`.
2. Open `http://localhost:8791/?play&at=delhi&dev&testdrive=1&q=low` (both `dev` and `testdrive=1` are needed).
3. In the page console (or from a browser tool), once: `await import('/src/debug/delhi_test_adapter.js')`. Without both flags it returns `{installed:false}` and does nothing. It gives `window.__test`.
4. If the import says "Failed to fetch": a service worker from an earlier visit is in the way. Run `for (const r of await navigator.serviceWorker.getRegistrations()) await r.unregister(); for (const k of await caches.keys()) await caches.delete(k); location.reload()`.

## Calls (all on `window.__test`)
| Call | What it does |
|---|---|
| `ready()` / `await whenReady(seconds)` | scene, Delhi pack, car and the game's router exist. A cold cache downloads about 100 MB first, so allow a minute or two |
| `setSpawn({landmarkId} or {lat,lon} or {x,z}, yaw?, maxM = 40)` | the game's own `nearestStreet` and `phys.reset`; refuses a point farther than `maxM` from any street (a landmark centre can be 120 m from one: pass `maxM` on purpose) |
| `setCamera({x,y,z,yaw,pitch})`, `returnToCar()` | the game's `__cam` fly view, and back |
| `await setControls({steer,throttle,brake,handbrake}, ms)` | holds W, A, S, D or Space as keyboard events through the game's own input handler, then releases (digital, not analogue) |
| `plan({landmarkId} ...)` | the game's `CityRouter.plan` from the car: metres, seconds, nodes, turn steps |
| `await followRoute(to, {maxSeconds, sampleMs, onSample})` | sets the route and drives it with the game's own autodrive; stops at arrival, at `maxSeconds`, or after 25 s without moving; returns a report (arrived, metres driven, minimum wheel contact, largest height step between samples, frame stats, console errors, route steps reached) |
| `telemetry()` | position, lat, lon, heading, speed, street and edge id, surface, wheel contact, ground height, impact, route state, draw calls, triangles, heap, recent frame times, error count. A field the game does not expose is `null` (`roadLevel`, `buildSha` today) |
| `capture(name, extra)` | the metadata record for a screenshot (the pane or runner takes the picture; this file cannot read the canvas) |
| `frameStats()`, `errors()`, `reset()` | frame percentiles (and hitches over 50 ms), page and console errors, release keys and clear the route and autodrive |

## Known limits (read before trusting a number)
- Frame times come from a visible tab on whatever machine runs it. A hidden tab, a laptop, or a Mac is not a phone. Do not quote them as device performance.
- Not built yet: photo comparison (T4), real-phone runs (T5), a crossing registry and level-aware road/rail overlap checks (needs C1's `surfaceAt` and C3/C4 data), pedestrian and traffic spawn detectors, sign text assertions.
- The stall detector cannot tell a red signal from a real stall (it waits 25 s). Treat a "stuck" as something to look at, not as a verdict.
- `followRoute` uses the game's autodrive, so it tests the road, the route and the car, not a person's steering.

## T2 and T3 (fixtures, headless runner, drive detectors)
- `tools/delhi_test_routes.json` is generated by `node tools/make_delhi_fixtures.mjs` from the pack, never typed: landmarks from `landmarks.json`, and the entry and exit nodes of the mapped flyover, underpass and tunnel runs found in `graph.json` (layers 1 and -1). A point from lat/lon that is not in the pack (the ITO junction) is `verified:false` and not asserted.
- `node tools/run_delhi_test.mjs [--fixture id] [--no-write]` is the **headless** half (no browser, 0.3 s): the points are near streets; the game's own `CityRouter` finds a route in a sane length; no one-way edge is travelled against its direction; the expected layered edges are on the route; the surface height (`deckHeight` minus `underDepth`) is continuous at every route node; Todarmal's fan and building overlap are recounted; the Delhi-wide ramp-slope audit and the count of turn restrictions in the pack are printed. The report goes to `reports/delhi-qa/<sha>/headless.json` (git-ignored). It is also one self-test check.
- The **drive** half runs in a browser: `await __test.runFixture('flyover-rani-jhansi', {time:'night', weather:'rain'})`. Detectors: arrived, no car below the ground, no road slope above 25 % between samples, wheel contact, no console errors, not stalled for 25 s, and the deck or floor of a flyover or underpass is reached. A run that only runs out of time is `INCONCLUSIVE`, not FAIL. A machine without WebGL cannot run this half: report `NOT RUN - ENVIRONMENT UNSUPPORTED`, never PASS.
- Spawning far from the car: the city streams only around the car, so `runFixture` puts the car at the fixture start (a spawn, not a drive) and waits up to 60 s for tiles.

**What the ramp finding means.** `deckHeight` climbs `LEVEL` (5.6 m) per layer over a ramp of at most half the edge's own length, with a smoothstep, so a short ramp edge climbs steeply: the steepest slope is 1.5 x height / ramp. The headless audit over the whole Delhi pack counts **2,153 drivable edges that carry a ramp end; 1,573 are steeper than 12 % and 1,283 steeper than 25 % at the steepest point (worst 105 %)** by that formula. Only the Rani Jhansi entry is confirmed by a drive; the other counts are the formula's result, not driven. The usual causes are short ramp stubs mapped as separate edges (16 to 60 m). This is C1 in `docs/CITY_CONFLICTS_PLAN.md` (Anshul's Claude): the fix is to lengthen a ramp across the chain of edges, not within one edge.

**Other facts the runner printed.** The pack holds **0 turn restrictions**, so the router cannot honour a no-right-turn or no-U-turn; the brief's "turn restrictions" item needs new data, not new code. Frame times during the drives (p50 11 to 28 ms, p95 17 to 78 ms at far districts while tiles streamed) are from this machine only.
